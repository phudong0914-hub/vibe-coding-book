🚀 Sổ tay Vibe Coding Thực Chiến

Thời gian đọc: 12 phút · Playbook Chuẩn Senior Engineer

1. Tổng Quan & Nguyên Tắc Cốt Lõi

Playbook này giúp bạn dùng AI coding agents như Codex, Claude Code, Cursor hoặc các agent tương tự một cách có kỷ luật hơn: vẫn giữ tốc độ vibe coding, nhưng có ngữ cảnh sạch, kế hoạch rõ, giao diện tốt, code dễ sửa, kiểm thử được và giảm rủi ro trước khi triển khai.

Công thức tổng quát: Reference → Context sạch → Product Spec → Implementation Plan → Design System → Build từng milestone → Verify/Refactor → Security Audit → Ship.

💡 Vì Sao Cần Một Quy Trình Vibe Coding?

Vibe coding rất mạnh khi bạn muốn biến ý tưởng thành sản phẩm nhanh. Bạn có thể đưa cho AI một URL mẫu, ảnh giao diện, tài liệu yêu cầu hoặc mô tả ngắn, rồi để AI đọc code, tạo file, chạy thử và tự sửa lỗi. Tuy nhiên, nếu thiếu quy trình, AI rất dễ tạo ra sản phẩm "trông có vẻ đúng" nhưng sai mục tiêu, giao diện chung chung, code khó bảo trì hoặc không sẵn sàng để ship.

Quy trình dưới đây tạo một đường ray rõ ràng để AI chạy nhanh hơn, đúng hơn và ít bị lạc hướng hơn. Bạn giữ vai trò quan trọng nhất: người định hướng sản phẩm, người duyệt chất lượng và người quyết định gu thẩm mỹ cuối cùng.

🎯 4 Nguyên Tắc Cốt Lõi

  1. 1. Context trước, code sau: AI chỉ làm tốt khi nhìn thấy đúng ngữ cảnh. Đưa cho AI tài liệu yêu cầu, reference, ảnh chụp, constraint kỹ thuật và tiêu chí hoàn thành trước khi gõ dòng code nào.
  2. 2. Milestone nhỏ tốt hơn làm tất cả một lần: Đừng yêu cầu AI làm toàn bộ app trong một lượt. Chia thành các mốc nhỏ có thể chạy được: layout trước, state sau, API sau nữa, rồi mới polish animation và responsive.
  3. 3. Design system trước khi polish UI: Định nghĩa bộ quy tắc màu, font, spacing, radius, shadow, state và motion trước để giao diện nhất quán và chuyên nghiệp ngay từ đầu.
  4. 4. Verify bằng bằng chứng, không chỉ cảm giác: Sau mỗi vòng build, kiểm tra lại bằng build log, test tự động, trình duyệt thật, ảnh chụp màn hình, responsive, console error và các trạng thái loading/empty/error.

2. Quy Trình Vibe Coding 7 Bước Chuẩn Senior

Bước 0: Chọn Đúng Kiểu Dự Án

Trước khi bắt đầu, xác định loại dự án để áp dụng workflow và tiêu chí kiểm tra phù hợp:

  • Clone/recreate website mẫu: Phân tích reference, chụp toàn trang, ghi lại animation và tái tạo bằng code mới.
  • Làm app/tool từ ý tưởng: Xác định product spec, luồng sử dụng, state, form, dữ liệu và trạng thái lỗi.
  • Làm SaaS/dashboard: Thiết kế information architecture, bảng dữ liệu, filter, chart, empty state và permission flow.
  • Làm game/3D/animation: Xây dựng gameplay loop, performance, input handling, camera, collision và test tương tác.
  • Sửa/refactor repo có sẵn: Đọc kiến trúc hiện tại, giới hạn phạm vi sửa và giữ nguyên behavior cũ.

Bước 1: Chuẩn Bị Ngữ Cảnh Sạch (Context Ingestion)

Biến mọi nguồn đầu vào thành tài liệu rõ ràng để AI đọc được: website mẫu, PDF, ảnh chụp, video quay màn hình, ghi chú hoặc repo hiện có.

Cấu trúc thư mục gợi ý:

/context/spec.md
/context/reference.md
/context/screenshots/
/context/constraints.md

Công cụ khuyến nghị: Firecrawl (crawl web ra Markdown), Crawl4AI (crawler RAG), OpenDataLoader PDF (bóc tách PDF/bảng biểu), Full-page screenshot.

Bước 2: Viết Product Spec & Agent Governance

Tạo file PRODUCT_SPEC.md để khóa mục tiêu sản phẩm và thiết lập kỷ luật không cho AI code bừa bãi.

Nội dung tối thiểu: Người dùng chính, Vấn đề cần giải quyết, Luồng sử dụng chính, Tính năng MVP, Phần bỏ qua ở v1, Tiêu chí hoàn thành.

Bước 3: Lập Implementation Plan

Tạo file IMPLEMENTATION_PLAN.md theo góc nhìn Senior Engineer để chia nhỏ dự án thành các mốc kiểm tra được.

Cấu trúc plan: Tech stack, Cấu trúc thư mục, Module chính, Data model, Local state/API, Test plan, Milestones, Rủi ro.

Bước 4: Tạo Design System Trước Khi Dựng UI

Quyết định tính thẩm mỹ chuyên nghiệp ngay từ đầu trước khi sinh nhiều component. Yêu cầu AI tạo DESIGN_SYSTEM.md và file CSS Tokens.

Nội dung Design System: Color tokens (HSL/Dark mode), Typography scale, Spacing scale, Radius, Shadow, Form/Button states, Responsive & Motion rules.

Bước 5: Build Theo Milestone Nhỏ

Thực hiện vibe coding theo từng mốc nhỏ. Mỗi milestone phải chạy kiểm thử thành công trước khi chuyển sang mốc tiếp theo.

  • Milestone 1: Layout chính, navigation, mock data.
  • Milestone 2: Form, filter, search hoặc tương tác chính.
  • Milestone 3: State management, API integration, data persistence.
  • Milestone 4: Responsive polish, empty/loading/error states.
  • Milestone 5: Micro-interactions, animation & final visual polish.

Bước 6: Verify, Review Và Refactor

Kiểm tra lại toàn bộ sản phẩm bằng chứng cứ (Build production, Console log, Layout mobile/desktop). Khi file vượt 300-500 dòng, yêu cầu AI tách thành các module độc lập nhưng giữ nguyên hành vi.

Bước 7: Security Audit Và Ship

Rà soát an ninh mạng trước khi triển khai công khai. Phân loại lỗi theo P0/P1/P2 và xử lý triệt để P0/P1 (Leak API key, XSS, Unsafe Input, Build error).

7. 15 Gợi Ý Lập Trình Theo Phong Cách Vibe

Bộ 15 gợi ý lập trình (prompts) thực chiến được đúc kết để tối ưu hóa sự cộng tác giữa bạn và AI Coding Agents ở mọi giai đoạn phát triển dự án. Công thức chung cực kỳ tinh gọn: Copy, điền thông tin trong ngoặc vuông [ ], và chạy. Dưới đây là bảng tổng quan và chi tiết từng prompt mẫu:

Mã số Gợi ý (Prompt) Trường hợp sử dụng (Use it when)
01 Write a Full PRD Trước khi phát triển bất kỳ tính năng mới nào
02 Create Your CLAUDE.md Thiết lập dự án mới, phiên làm việc đầu tiên
03 Ultra Plan Mode Tác vụ phức tạp ảnh hưởng nhiều file
04 Spec-Driven Development Các tính năng quan trọng không được phép sai lệch
05 Full UI & UX Design Brief Trước khi thiết kế màn hình hoặc luồng người dùng
06 Implementation Plan Sau khi tài liệu đặc tả (Spec) được phê duyệt
07 Wire Up an MCP Server Kết nối AI Agent với các công cụ/hệ thống bên ngoài
08 Connect Your Database Thiết lập cơ sở dữ liệu (Postgres / Supabase...)
09 Find Security Gaps Rà soát bảo mật trước khi deploy lên production
10 Debug an Error Fast Ngay khi xuất hiện lỗi/bug trong quá trình phát triển
11 E2E Test Your Application Đảm bảo an toàn cho các luồng giao dịch/dòng tiền
12 Clean Up Dead Code Khi kho mã nguồn bắt đầu nặng nề và dư thừa
13 Write Clean Git Commits Mỗi lần commit code lên Git repository
14 Hooks as Guardrails Tự động hóa kiểm soát chất lượng bằng các script
15 Turn a Task Into a Skill Khi một tác vụ lặp lại từ 3 lần trở lên
01 -- Write a Full PRD 
Write a complete PRD for the feature below.

Feature: [DESCRIBE FEATURE]
Users: [WHO USES IT]
Stack: [YOUR STACK]

Include:

* Problem statement + success metrics
* User stories with acceptance criteria
* Scope: what ships in v1, what does not
* Data model changes
* Edge cases + failure states
* Open questions for me to answer

Keep it under 2 pages. Be specific, no filler.
Save it as docs/prd-[feature].md so every later
prompt can reference it.
02 -- Create Your CLAUDE.md 
Scan this entire codebase, then generate a CLAUDE.md.

Include:

* What this project is, in 2 lines
* Tech stack + the versions that matter
* Commands: [DEV / BUILD / TEST / LINT]
* Architecture: where things live and why
* Code conventions you actually detect in the code
* Hard rules: [YOUR NON-NEGOTIABLES] -- what to
  never touch without asking
* Gotchas a new engineer would hit in week 1

Write rules as short imperatives. Nothing generic --
only what is true for THIS repo. If you are unsure
about a rule, ask me instead of inventing it.
03 -- Ultra Plan Mode 
Enter plan mode. Do NOT write any code yet.

Task: [PASTE TASK]
Constraints: [DEADLINE / STACK / NO-GO ZONES]

1. Read every file this task touches, list them
   with one line on what each does today
2. Map current behavior vs target behavior
3. Propose 2-3 approaches with real tradeoffs:
   complexity, risk, blast radius
4. Pick one and justify it in 3 lines
5. Break it into steps small enough to verify
   one at a time, each with its own check
6. List risks + the exact rollback for each
7. Flag anything touching [AUTH / PAYMENTS /
   PROD DATA] for my explicit sign-off

Then stop. Show me the plan and wait for my
approval before touching a single file.
04 -- Spec-Driven Development 
We build specs first. Write a spec for: [FEATURE]

Context: [WHO USES IT + WHY NOW]

Spec format:

* Behavior: given / when / then, every case --
  happy path, edge cases, failure states
* API contract: inputs, outputs, error shapes,
  status codes
* Data: schema changes + migrations needed
* UI states: loading, empty, error, success
* Non-goals: what this spec deliberately skips
* Acceptance checklist I can verify line by line

After I approve the spec, implement EXACTLY the
spec. If reality forces a deviation, stop, update
the spec, get my ok, then continue. The spec is
the source of truth, not the code.
05 -- Full UI & UX Design Brief 
Create a full UI/UX design brief for: [SCREEN OR FLOW]

Audience: [USERS]
Brand: [COLORS / FONTS / VIBE]

Deliver:

* User journey through the flow, step by step
* Layout per screen: hierarchy, spacing, breakpoints
* Component inventory with every state --
  hover, empty, error, loading
* Typography + color tokens
* Motion: what animates, duration, easing
* Accessibility notes

Study patterns from [2-3 PRODUCTS YOU ADMIRE]
for direction. Never copy them.
06 -- Implementation Plan 
Create an implementation plan for: [APPROVED
SPEC / PRD]

Rules:

* Sequence steps so the app compiles and runs
  after EVERY single step
* Each step: files touched, what changes,
  how I verify it works
* Flag steps needing a migration or new dependency
* Put the riskiest unknowns first
* Size each step: [S / M / L]

Output a numbered build sequence I can run one
step at a time. Wait for my "go" between steps.
07 -- Wire Up an MCP Server 
Wire up an MCP server for: [SERVICE / API]

What I need it to do: [JOBS TO BE DONE]

1. Check for an official or well-maintained
   existing server first -- name your source
2. If one exists: exact install command + the
   .mcp.json config, scoped to this project
3. If not: scaffold one with the MCP SDK --
   tools, auth, error handling, typed responses
4. Add ONLY the tools I will actually use: [LIST]
5. Wire secrets through [ENV VARS], never
   hardcode keys in the config file
6. Verify the connection and call one tool
   end to end, show me the output
7. Document each tool in 1 line so future
   sessions know when to reach for it
08 -- Connect Your Database 
Connect this app to [POSTGRES / SUPABASE / YOUR DB].

* Pick the client that fits this stack,
  justify it in 1 line
* Env vars: name them, add to .env.example,
  never commit real values
* Schema: tables for [ENTITIES] with types,
  relations, and indexes for [HOT QUERIES]
* Create + run the migrations, and show me
  the rollback for each one
* One typed query helper per table -- no raw
  SQL scattered through components
* Access rules / row-level security if this
  is [MULTI-TENANT]
* Connection pooling if we are serverless

Then prove it: seed one row, read it back,
show me the output.
09 -- Find Security Gaps 
Audit this codebase for security gaps.
Attack it like you want in.

Focus areas: [AUTH / PAYMENTS / USER DATA]

Check:

* Secrets in code, config, or git history
* Injection: SQL, XSS, command, path traversal
* Auth: routes missing checks, weak sessions,
  broken redirects
* IDOR: can user A read user B's data?
* File uploads + input validation on every form
* Dependency CVEs -- run the audit, read it
* Rate limiting on [EXPENSIVE ENDPOINTS]
* What leaks through error messages and logs

Rank findings by severity with exact file:line,
fix the critical ones now, and list the rest
as tickets with effort estimates.
10 -- Debug an Error Fast 
Debug this error. Do NOT guess.

Error: [PASTE FULL ERROR + STACK TRACE]
When it happens: [STEPS TO REPRODUCE]

1. Read the stack trace, open the exact files
   involved
2. State expected vs actual behavior in 1 line
3. List 3 hypotheses, ranked by likelihood
4. Prove or kill each one with logs or a tiny
   test -- evidence, not vibes
5. Fix the root cause, not the symptom
6. Search the repo for the same pattern -- if
   it can break here, it breaks elsewhere
7. Add a regression test that fails without
   the fix
8. Tell me in 2 lines why it broke and why it
   can never break this way again
11 -- E2E Test Your Application 
Write Playwright E2E tests for: [FLOW]

Stack: [YOUR STACK] CI: [GITHUB ACTIONS / OTHER]

* Money paths first: [SIGNUP / CHECKOUT /
  CORE ACTION]
* Test what the user sees, not implementation
  details
* Selectors: roles and labels, never brittle
  CSS chains
* One unhappy path per flow: bad input,
  network failure, expired session
* Tests stay independent -- any order, zero
  shared state, each seeds its own data
* Headless in CI, headed locally for debugging
* Screenshots + traces on failure only

Run the suite, show me the results, fix what
fails, and tell me what the suite still does
NOT cover.
12 -- Clean Up Dead Code 
Find and delete dead code in this repo.

Scope: [WHOLE REPO / SPECIFIC FOLDER]

* Unused exports, components, hooks, utils
* Unreachable branches + commented-out blocks
* package.json dependencies nothing imports
* Stale feature flags stuck always-on or
  always-off
* Duplicate logic that should merge into one
* Dead CSS classes and unused assets

Verify with a search before EVERY deletion --
dynamic imports and string references count.
Delete in small commits, run [BUILD + TESTS]
after each one, and report total lines removed
plus anything you were not 100% sure about.
13 -- Write Clean Git Commits 
Commit my staged changes properly.

Convention: [CONVENTIONAL COMMITS / YOUR FORMAT]

* Split unrelated changes into separate commits
* Format: type(scope): what changed and why
  feat / fix / refactor / chore / docs / test
* Subject under 50 chars, imperative mood
* Body explains the WHY, wrapped at 72
* Reference the ticket: [TICKET-ID]
* Never mix a refactor with a behavior change
  in one commit
* Never commit [SECRETS / .ENV / GENERATED
  FILES]

Show me the plan -- files per commit + messages --
before you commit anything. Then commit one at
a time so I can stop you between them.
14 -- Hooks as Guardrails 
Set up Claude Code hooks as guardrails here.

Stack: [YOUR STACK + PACKAGE MANAGER]

* PostToolUse: run [LINT + TYPECHECK] after
  every file edit, feed errors straight back
* PreToolUse: block edits to [PROTECTED PATHS:
  MIGRATIONS, .ENV, PROD CONFIG]
* Stop: run [TEST SUITE] before a session ends
* Notification: ping me with [SOUND / SLACK]
  when my input is needed

Write the hook scripts + the settings.json
entries. Keep each script under 20 lines and
exit non-zero with a clear message so the
agent knows exactly what to fix. Then trigger
each hook on purpose and show me it firing.
15 -- Turn a Task Into a Skill 
Turn this repetitive task into a Claude Code skill.

The task I keep doing: [DESCRIBE TASK + STEPS]

* Create .claude/skills/[NAME]/SKILL.md
* Frontmatter: name + description with the exact
  trigger phrases I actually say
* Body: numbered workflow, my conventions,
  edge cases
* What it should ask me for vs infer on its own
* What "done" looks like

Then dry-run the skill on a real example and
refine until the output matches how I do it
by hand.

8. Checklist Kiểm Tra Trước Khi Ship

Bảng kiểm tra 4 khía cạnh tiêu chuẩn sản phẩm trước khi đưa ra người dùng thật:

📦 Product

  • Luồng chính dùng được từ đầu tới cuối.
  • CTA, form, navigation và trạng thái lỗi rõ ràng.
  • Không còn placeholder gây hiểu nhầm.

🎨 UI/UX

  • Desktop và mobile không vỡ layout.
  • Text không tràn, không chồng lên nhau.
  • Motion có ích, không làm trang nặng.

💻 Code

  • Build production thành công.
  • Component lớn đã được tách hợp lý.
  • Không có console error quan trọng.

🔒 Security

  • Không leak API key hoặc file .env.
  • Input được validate.
  • Không render HTML user nhập một cách unsafe.

9. Lỗi Thường Gặp & Bài Học Thực Chiến

Những bẫy phổ biến làm dự án vibe coding bị thất bại hoặc mất thời gian debug:

  • ❌ Bắt đầu bằng "làm app này cho tôi": Không có spec khiến AI tự suy đoán tính năng sai lệch.
  • ❌ Nhồi quá nhiều context rối: Làm AI bị nhiễu thông tin ở giữa hoặc nhầm lẫn giữa các phiên bản.
  • ❌ Yêu cầu làm toàn bộ dự án 1 lần: Code sinh ra quá lớn, vỡ logic và cực kỳ khó tìm vết để fix.
  • ❌ Bỏ qua Design System: Giao diện sinh ra mang cảm giác mờ nhạt, xám xịt như template mặc định.
  • ❌ Chỉ tin lời nói của AI mà không chạy thử: AI báo "đã fix lỗi" nhưng thực tế build bị crash.
  • ❌ Đợi cuối dự án mới refactor: Code phình to trên 1000 dòng khiến việc chia tách bị vỡ behavior.
  • ❌ Tuyên bố "an toàn 100%": Không thực hiện audit lỗ hổng thực tế trước khi push public.

10. Kết Luận & Định Hướng Vận Hành

Vibe coding hiệu quả không phải là để AI làm mọi thứ một phát rồi hy vọng kết quả đúng. Cách làm tốt hơn là để AI chạy nhanh trong một quy trình rõ ràng: context sạch, spec rõ, plan nhỏ, design system tốt, build từng milestone, verify liên tục, refactor đúng lúc và audit trước khi ship.

Khi đó, bạn không chỉ "chat với AI để code", mà đang vận hành một quy trình sản xuất phần mềm nhẹ, nhanh và có khả năng lặp lại. AI là người tăng tốc. Bạn là người giữ mục tiêu, chất lượng và gu sản phẩm.
